# Trusted ranking evidence reader (Issue #10)

This is an internal trusted data-input layer for the scorer described in
[RANKING.md](RANKING.md). It does not implement an HTTP endpoint.

## Contract and limitations


`SqlAlchemyRankingEvidenceRepository` in `ranking/evidence.py` provides
internal `pregame(game_id, as_of=...)` and `postgame(game_id, as_of=...)`
methods, returning a `VersionedScore` or `None` when trust is insufficient.
The caller supplies a canonical game UUID and an as-of moment, **not** a
client-claimed tip, finish time, source timestamp, normalized signal, or
postgame disclosure preference. The repository first finds the latest
historically knowable NBA game observation, then validates its status.
A pregame score requires a scheduled observation known strictly before
the trusted scheduled tip and an as-of cursor earlier than that tip.
A scheduled row carrying a result score, actual tip or final timestamp is
inconsistent and cannot support pregame ranking. Postgame requires a latest
`final` observation with an explicit, trustworthy `final_at` no later
than the observed/available timestamps **and strictly after every known
scheduled/actual tip**. Missing final-clock provenance is not inferred
from a provider status or scheduled duration.
TheSportsDB's current final observations have no `final_at`; these
correctly yield no postgame score until evidence quality improves.

Only carefully curated `TemporalFactRecord` rows with
`subject_type="game"`, canonical `game_id`, and an exact signal name
`ranking.pregame.<PregameSignal.value>` or
`ranking.postgame.<PostgameSignal.value>` are read. A trusted normalizer
must write `value={"normalized_value": 0.0..1.0}`, original `source_id`,
`observed_at`, `available_at`, `valid_from` and optional `valid_to`.
That number represents a **normalized feature**, never a game score.
Historical reads require both observation and availability no later than
the requested as-of time and fact validity covering that moment.
The newest knowable revision per signal wins; a malformed revision masks
older values instead of resurrecting stale evidence. Competing observations
with identical latest observed/available timestamps fail closed, rather than
choosing a tip or final state by a random UUID. Likewise, tied revisions of
a ranking signal are omitted; independent untied signals may still be scored.
When observed timestamps match but availability differs, the later-available
observation takes precedence only once it is knowable. Missing or invalid
features are omitted; no current records, other leagues, title text, winner,
margin or final score are silently converted to interest/entertainment.
Each score component refers back to its persisted source and fact UUID.

### Current source-review gate (Issue #10)

The reader now requires the source registry's **current**
`verification_status="verified"` for the latest knowable game observation
and for each latest curated feature revision. Source verification is checked
**after** as-of revision selection: a newer unreviewed game observation masks
older scheduled/final state; an unreviewed feature update masks an older
verified value instead of silently resurrecting it. Independent verified
signals can still produce a partial score. A source being disabled for new
collection does not alone invalidate old already-observed evidence.

This is a fail-closed source-review prerequisite, **not** proof that a source
is licensed, that a historical source was approved at the time of capture, or
that a derived normalized signal accurately represents NBA play. Current
registry verification is not itself versioned; an owner-reviewed historical
source approval/audit trail and independent feature producers remain open
requirements. No real-score production or new user-visible disclosure is
activated by this change.

These records are **not** automatically generated by TheSportsDB ingestion.
Live-normalizer work must define, vet and test quantitative derivation for each
signal separately before emitting facts. The evidence reader returns
internal scores only and does not archive them or provide any public endpoint.
In particular, postgame order and time-budget choices remain unavailable
from public APIs without explicit informed opt-in and policy-gated
disclosure. No favorite-team weighting or media-cursor changes occur.

PostgreSQL integration tests:
`cd backend && pytest -q tests/integration/test_ranking_evidence.py`.
They cover delayed/backfilled signals, tip boundaries, correction of
scheduled status, malformed and tied revisions, conflicting game statuses,
availability tie-breaking, finalization trust, contradictory scheduled-game
fields and impossible final/tip ordering, pre-final and future postgame facts,
unreviewed latest game/feature sources, and non-NBA identities. The consent-gated recommendation endpoint
is documented in RANKING.md and was implemented separately in PR #33;
trusted feature producers, calibration, front-end disclosure and live Neon
validation remain separate follow-up work.

## TheSportsDB overtime signal candidate (Issue #10)

`ranking/feature_candidates.py` now contains the **pure, read-only**
`thesportsdb_overtime_candidate` function. It consumes the existing
`normalize_thesportsdb_event` result, which accepts only league ID 4387 (NBA)
and retains the provider's original `strStatus` in
`metadata["provider_status"]`. It yields an immutable, provider-scoped
`OvertimeCandidate` **only** for a finished `AOT` event with both scores.
TheSportsDB's [basketball event-status guide](https://api.thesportsdb.com/docs_api_data)
defines `AOT` as finished after overtime, `OT` as overtime **in progress**,
and `FT` as finished. The independent [March 25, 2026 Pistons/Hawks
event](https://www.thesportsdb.com/event/2358414-detroit-pistons-vs-atlanta-hawks)
shows `AOT` and an overtime-period score. This is documentation and public
event-page corroboration, **not** a live authenticated API-payload test.

- **Derivation:** normalized `status="final"`, preserved raw code `AOT`,
  two nonnegative integer scores => `overtime_occurred=True`, a *binary
  event indicator*, not a calibrated quality/watchability value. `FT`,
  generic `FINAL`, `OT`, unsupported/changed codes, missing scores or
  inconsistent statuses yield **no candidate**; they are not treated as a
  proven zero-overtime event. An unknown value is never guessed from game
  length, points, result margin, period count or highlights.
- **Identity/provenance:** the candidate has `provider="thesportsdb"` and
  the provider's event ID only. A future producer must resolve that ID to a
  canonical NBA `game_id`, choose the latest knowable version and ensure
  current/source-at-capture approval. This pure function does not perform
  those trust checks. A source's verification flag does not validate the
  individual basketball claim or prove rights in a particular payload.
- **Time:** raw `strTimestamp` denotes *scheduled tip*, **not** actual game
  end or first knowledge of overtime. TheSportsDB's event status has no
  authenticated event-final timestamp here. A future fact must use the
  recorded capture/observation and defensible availability time, preserve
  subsequent status corrections, and must not predate first reliable
  observation. `final_at` still needs independent evidence before any
  postgame scorer accepts it.
- **Rights:** [TheSportsDB's terms updated September 17, 2026](https://api.thesportsdb.com/docs_terms_of_use.php)
  allow use/copy/modification of content from official API endpoints subject
  to third-party rights, require a paid subscription for app-store release,
  and impose source attribution for paid API services. The terms prohibit
  website scraping and do not clear third-party artwork. This code makes
  **no network request** and stores no third-party payload; production
  capture/retention/distribution and license needs must still be approved
  for the intended deployment.
- **Activation gate:** the result is deliberately **not**
  `FeatureObservation`, a `TemporalFactRecord` or a `VersionedScore`.
  Neither the archive script nor any API uses it. Before producing
  `ranking.postgame.overtime` facts, independently validate real API
  status coverage/corrections, historical time semantics, source approval
  and binary-feature calibration (including missing and non-overtime cases).
  Do not expose postgame ordering or score to a sealed-game user.

Offline tests: `cd backend && pytest -q tests/test_ranking_feature_candidates.py`.
No live source request, Neon connection, production model calibration or
user-facing watchability claim is implied by those tests.

## Explicit score materialization (PR #37)

The internal `RankingMaterializationService` in
`ranking/materialize.py` connects this trusted reader to
`SqlAlchemyRankingStore.archive`. It requires a canonical UUID, a typed
`pregame` or `postgame` family and a **timezone-aware, explicit** `as_of`
instant. It verifies the returned game, score family, current model version,
snapshot time and component timestamps before invoking the append-only archive.
A missing, malformed or not-yet-observed feature is **not** imputed: when the
reader returns no score, nothing is written. The caller owns the transaction;
the existing archive rejects changing an already archived
`(game, kind, version, as_of)` snapshot rather than overwriting history.

For a one-game operational run from `backend/`, with migrations applied and
`DATABASE_URL` configured, use:

```bash
python scripts/archive_ranking.py \
  --game-id 11111111-1111-4111-8111-111111111111 \
  --kind pregame --as-of 2026-05-04T23:00:00+00:00
```

The UUID and date above are **illustrative**, not evidence of a real NBA
game. To archive postgame, explicitly use `--kind postgame` and a historical
instant after a trusted final and post-final feature observations. A missing
`final_at` or missing curated normalized features results in no archive;
the script never infers them from score, game duration or real-world now.
The CLI prints only whether a trusted snapshot was archived or unavailable,
not the internal value/components. It is an operator tool, not an API or
permission mechanism. Public postgame ordering still requires per-request
consent at the existing `/recommendations/watchability` endpoint; the general
dashboard remains sealed unless its spoiler policy explicitly allows a layer.

Unit checks: `pytest -q tests/test_ranking_materialize.py`. PostgreSQL
integration: `pytest -q tests/integration/test_ranking_materialization_persistence.py`.
No production feature producer, live data coverage or calibrated score is
claimed by this wiring slice.
