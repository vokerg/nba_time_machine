# NBA.com play-by-play access and watchability evidence — Issue #80

Research date: **2026-10-13**. Scope: read-only research and implementation handoff; **not** source approval or collector activation.

## Decision

**Conditional technical GO for a bounded, owner-run proof of concept; NO-GO for production NBA.com ingestion or real watchability ratings today.** NBA.com publicly displays useful summary and play-by-play pages, and community-maintained `nba_api` documents plausible first-party JSON surfaces. However, a complete 2025/26 game action feed has **not** been fetched and verified from this execution environment, reliable backend HTTP access is **not** demonstrated, the observed feed does **not** establish an authoritative final timestamp, and NBA terms constrain reuse. Neither missing data nor an inaccessible endpoint should yield a low-quality rating.

For a documented, authenticated alternative, BALLDONTLIE has a GOAT-only `/v1/plays` endpoint, with game/clock/score/wallclock events starting in the **2025 season** (i.e. verify 2025/26 coverage with credentials). The advertised GOAT price is $39.99/month as inspected on this date; the listed rate limit is 600 requests/minute outside the trial. BALLDONTLIE's **2026-09-17 Terms §6** explicitly permit caching, storage, archiving, analysis, redistribution and derivative works of lawfully obtained API Data, including commercial use, subject to restrictions on competing services and unmodified raw resale. §11 explicitly says the provider cannot clear every third-party right. Thus this is a comparatively strong **API-contract route**, not blanket league permission. A no-cost NBA.com backend path is **not verified**.

It **does not** attempt to evade 403/anti-bot measures, follow redirects, or activate collection. Example:

```bash

In the owner's ordinary browser, manually open the official play-by-play URL, select **ALL**, inspect Q4/OT and use DevTools Network (Fetch/XHR) to identify the site's actual response **without exporting session cookies**. Compare against the separately run backend probe; a browser request may work where server-side fetch does not. No CAPTCHA, paywall or security-warning bypass.

## Source options and contracts

1. **NBA liveData JSON**: `https://cdn.nba.com/static/json/liveData/playbyplay/playbyplay_{gameId}.json`, `.../boxscore/boxscore_{gameId}.json`, optional `.../scoreboard/todaysScoreboard_00.json`. Community-documented schema: root `game.gameId`, `game.actions[]`, period, `clock` (`PT11M58.00S`), `scoreHome`/`scoreAway`, `actionNumber`, `orderNumber`, `actionType`, `timeActual`, `edited`. Current response access blocked/unavailable. Verify all keys against **actual captured responses**; example shape in `swar/nba_api` is NOT this season's observed response.
2. **NBA Stats V3**: `https://stats.nba.com/stats/playbyplayv3?GameID={gameId}&StartPeriod=0&EndPeriod=0` (and period subsets for reconciliation). Community documentation reports `game.actions`, period, clock, team IDs and scores; no successful live probe here. **Do not use V2 as preferred fallback**: `swar/nba_api` notes V2 was deprecated in 2024/25 and may return empty JSON. Website-internal interfaces are not official supported developer contracts.
3. **Official NBA.com summary, box score, game charts and game-book PDF**: useful independent ground truth for final scoreboard, period totals, lead-change count, biggest lead, OT count, and player box scores. Static/JS access and game-book URLs must be verified independently. A score summary lacks clutch-by-minute resolution, game-action timestamps and trustworthy exact `final_at`.
4. **BALLDONTLIE**: documented `https://api.balldontlie.io/v1/plays?game_id={BDL-ID}`, `Authorization: <key>`, chronological `order`, `period`, `clock`, `home_score`, `away_score`, `wallclock`; separate game/box score/lineup endpoints. Provider IDs **are not** NBA game IDs. Auth/key and GOAT access required. The 48-hour trial still requires a payment method and is advertised as 5 req/min. Its [2026-09-17 Terms §§6–7, 11](https://www.balldontlie.io/terms.html) explicitly allow caching, archiving, analysis and derived products of lawfully accessed data, **without extra case-by-case provider approval**, but exclude competing services, raw unmodified resale, API-key sharing/bypass and imply no NBA/third-party IP clearance. Validate coverage, retention constraints and intended app use under the full terms.
5. **Sportradar NBA v8**: [documented Game Play-by-Play](https://developer.sportradar.com/basketball/reference/nba-play-by-play) endpoint `GET https://api.sportradar.com/nba/{access_level}/v8/{language_code}/games/{game_id}/pbp.{format}`; separate [Game Summary](https://developer.sportradar.com/basketball/reference/nba-game-summary). API key and agreement required; 3-second cache while in progress, 600-second when closed, and more after 7 days are **documented cache TTLs, not completeness or throughput guarantees**. Supports `complete` and `closed` states and league reference mapping; no authentic final-at clock established here. Plan pricing and historical 2025/26 access unverified.
6. **SportsDataIO NBA**: [documented Final PBP](https://sportsdata.io/developers/api-documentation/nba) `GET https://api.sportsdata.io/v3/nba/pbp/json/PlayByPlayFinal/{gameid}`; also Live/Final and Delta and separate game/player stats. API subscription required and their public free trial is **not** NBA play-by-play access. A `Final` endpoint gives a useful state/validation contract but **not** a trusted physical final timestamp by itself. Quote, history, actual payload, rights and operational SLA unverified.
7. **ESPN's website feeds, community mirrors and scrapes**: potential comparison sources, but undocumented/stability/redistribution/terms are not established here. They are **not** approved replacements merely because reachable.

**Further facts available if approved:** game and player box-score statistics, quarter/OT lines, shot locations and shot charts where provided, participant/team IDs, substitutions and on-court lineup candidates, fouls/turnovers, standings/schedule, and official game books. Some of these require separate endpoints and cannot be inferred from scores alone. Per-game source coverage must be measured rather than assumed.

### Rights/access decision

NBA.com's [§9](https://www.nba.com/termsofuse) requires attribution for NBA Statistics and limits use to legitimate news reporting or private non-commercial purposes; it prohibits their use in certain commercial products, play-by-play presentation, and a comprehensive regularly updated stats database without express prior consent. **Private use is not blanket permission to bulk download or indefinitely retain full feeds.** A noncommercial *derived watchability scalar* is not automatically the same as a full game reproduction, but its extraction, repeated capture and deployment still require explicit review. Review §9 alongside other general site/access terms before approving a specific collection method. Do not represent web accessibility as a license.

Pending review: source remains **disabled/unverified**, no full payloads, play descriptions, screenshots or PDF archives committed. Proposed owner-approved policy initially `metadata_only` for provenance/probe health only; permit aggregate derived facts solely after legal/product review. If full-event storage is needed to enable corrections/recomputation, negotiate documented rights/retention rather than silently switching to `full`. In contrast, BALLDONTLIE's [published §6 Terms](https://www.balldontlie.io/terms.html) expressly grant rights to archive, analyze and make derivative products from **lawfully retrieved Data**, including commercial use and redistribution; §7 limits automated access to official interfaces and prohibits bypass/key sharing; §11 reserves third-party IP questions. This is materially clearer provider-granted permission than NBA.com scraping, but still review full Terms, third-party rights, actual plan and app use. No real scoring until authorized access, data validation and calibration are complete.

## Feature derivation proposal (no fabricated watchability)

All game-event features require stable period order, period clock, monotonically advancing elapsed time (after interpreting countdown clock), home/away IDs, scores, revision handling, and **complete** period-boundary coverage. Missing or contradictory data => signal unavailable, not zero. Independently confirm source-provided count/quarter totals against computed values before accepting.

| Feature / candidate | Algorithm and required fields | Failure/correction / confidence |
| --- | --- | --- |
| Clutch minutes (postgame) | Construct piecewise-constant score differential through final **5:00 of Q4** and **all overtime**. Sum seconds with absolute margin <= 5, integrate per interval bounded by period ends. Normalize by eligible seconds; record raw seconds and coverage. Needs each scoring state, ordered clock and Q4/OT boundary scores. | Missing boundaries, reversed clocks or gaps => unknown. Must not count 4Q garbage time based on final margin alone. All-OT treatment/5-point definition should be versioned and calibrated. |
| Lead changes | Ignore tied states, count sign transitions between two *nonzero* score differentials after deduplicating corrections; 0-to-first-leader is not a change. Compare the official page's count but allow for documented definition differences. | Ambiguous corrections/order => unknown, don't prefer whichever count looks larger. |
| Comeback size | For the **eventual winner**, max earlier deficit `max(0, opponentScore - winnerScore)` over verified event scores, and separately final-quarter/OT max deficits. Needs verified final winner and full score trajectory. | Tie/abandonment, missing winner, incomplete period => unknown; winner-relative comeback differs from biggest lead. |
| Overtime | Number of confirmed period segments beyond period 4; binary `ot>=1` when confirmed, optionally extra OT indicator; requires declared period count and final result. | A final game with complete regulation and no OT => true zero; a missing OT segment never implies zero. |
| Individual performance | Compare verified player box-score totals (points, rebounds, assists, etc.) to reviewed, season-and-role-specific percentile baselines. Keep provenance and baseline version. | No box score or baseline => unknown; arbitrary headline / recap superlatives not quantitative evidence. |
| Rarity/stakes | Separate historical rarity, team stakes and playoffs context computed from **historically available** baselines and standings, with explicit versions. | Requires more sources and historical pregame truth; don't infer from postgame text as if it was pre-tip. |
| Tactical/game quality | **Not implemented automatically**. Requires independent validated signals / expert annotation, not an LLM adjective parsed from recaps. | Unknown until validated. |

Normalization to `ranking.postgame.{clutch,lead_changes,comeback,overtime,individual_performance,rarity,game_quality}` must be calibrated on diverse real labeled games. Existing `ranking/scoring.py` weights are a starting model, **not** validation. Model-version changes must produce separately versioned score archives; never rewrite prior decisions.

### Watchability calibration and quality controls

Keep the feature producer **interpretable** before any learned calibration. A game with a 25-point comeback can still be uncompetitive for three quarters; overtime is a signal, not automatic top ranking. Retain distinct diagnostics (full-game competitiveness, fourth-quarter/clutch tension, late lead swings, winner's maximum deficit, confirmed overtime count, exceptional-player box score) and feed calibrated, versioned 0..1 feature transforms into the existing `PostgameSignal` slots. Compare `clutch` minutes vs `lead_changes` correlation to avoid rewarding the same single late swing twice; check that blowouts with isolated star performances do not outrank genuinely compelling finishes merely because the player scored a lot.

**Evaluation requirement:** label a blind stratified sample from 2025/26: ordinary games, one-sided games, close-but-boring games, competitive games, late comebacks, 1OT, 2OT, playoffs and individual outliers. Gather at least two independent human watchability rankings per selected set; log disagreements rather than tuning exclusively on famous highlights. Measure rank agreement, top-N precision, coverage, sensitivity to missing PBP and stability under corrected data. This creates a baseline before deciding numerical tier thresholds, not a fabricated `9.8` score. AI may summarize only pre-cleared, policy-allowed reasons; it must never invent unmeasured tactical quality.

### Identity and temporal truth

1. Map NBA 10-digit `gameId` to the existing canonical UUID through `SportsExternalIdentityRecord(provider_key="nba", entity_type="game", external_id=...)`. Join to TheSportsDB canonical game using season + unambiguous home and away **verified team mappings** + scheduled local day/UTC tip with schedule shift tolerance. **Fail closed on duplicate/ambiguous matching**; never create a parallel game for the same real matchup. Validate playoff/cup/game-type IDs; NBA ID prefix alone isn't enough to authorize a season or match.
2. Store distinct: game period clock (not wall time), `timeActual` per event (provider assertion; possibly edited), `edited` (correction time), scheduled tip, actual tip if independently known, last terminal event time, independently trusted actual finish if any, **first confirmed final observation**, collection `observed_at`/`captured_at`, public `available_at`, `published_at` if explicitly provided. `gameStatus=3`, final score, Q4 endmarker and last `timeActual` **alone do not prove exact `final_at`**.
3. Existing `GameObservationRecord.final_at` is deliberately required by `SqlAlchemyRankingEvidenceRepository.postgame`. Today's TheSportsDB importer sets it null. Do **not** synthesize it using `scheduled_tip+2h`, source capture time, recap timestamp or final game-clock 0:00. If first reliable **final confirmation** is allowed as a distinct activation boundary, make an explicit reviewed product/schema/reader change; do not conflate it with physical final whistle.
4. Historical backfills captured in October 2026 are known to **this system** in October 2026. They cannot create a May 2026 pre-tip observed slate or score publication timestamp. The existing ranking/selection API also requires a historically knowable pregame slate. To expose 2025/26 replay safely, product must explicitly define a **retrospective replay mode** with a separate clearly labeled reconstructed timeline contract and spoiler guard (or import independently verified period-accurate archived evidence). Never silently backdate `available_at` or disable the consent gate.

### Operational ingestion contract, **after** source approval

- **Method/auth**: approved API client behind `sports/`, configurable credential only where contracted; no browser automation / bypass as silent backend dependency. No production requests today.
- **Cadence**: historical approved backfill one game per bounded request batch; live polling strictly under provider's explicit limits with exponential backoff on 429/5xx, `Retry-After` support, bounded max attempts and one per-source failure isolation. No implied NBA first-party rate/SLA: **unknown**.
- **Identity/dedup**: unique provider game ID + action ID/order + observed source revision; versioned corrections append snapshots, reconcile by stable event identity, don't double count score; source hash must not substitute game matching.
- **Timestamp**: capture UTC now, source wallclock and edit time only as claims, earliest knowability no earlier than defensible reliable observation unless historically proven.
- **Retention**: source-registry gate + rights-approved policy checked at write time; until then `metadata_only` and probe logs only. Never put raw action text, boxscore contents or tokens in CI/logs.
- **Validation gate**: full period sequence (4 + actual OT count), usable start/end markers, final totals match independently sourced official NBA summary/box-score, monotonic timeline, unique actions, score sanity, field/correction coverage, authoritative identity, source policy and final-time proof. A mismatch quarantines game; log coverage counts, not scores, to avoid spoilers.
- **Persistence**: approved captured material (if permitted) → existing source/capture provenance → existing `GameObservationRecord`/`TemporalFactRecord` → `SqlAlchemyRankingEvidenceRepository` → `RankingMaterializationService` → versioned archive → consent-gated coarse verdict and deeper why. Never direct source-to-API scoring.
